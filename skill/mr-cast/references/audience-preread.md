# A reviewer who reads the code next (`--audience preread`)

The viewer will review the code right after the video, so the video builds the model in their head and hands them the code in order. It follows the article's reviewer order, with these changes:

- **No code on screen.** No `code` scene, and no code cell in a `compare`. Identifiers and file names may appear on screen; expressions and code lines may not. Say them in words instead: "status pending, next try in 10 s". Label each diagram with the real identifiers and file names, such as `` `checkLimit` `` and `` `limiter.ts` ``, so the viewer can map the picture onto the code. Put the facts a code line would show, such as limits, keys, conditions and order, into the labels and the narration with their real values. A reading item's `check` and a terminal session may name operators and identifiers as inline code, such as "`>=` on (created_at, id)".
- **Draw what the code does, as the article says it,** not what it is meant to do. Where they differ, the reading item says what to check there.
- **Name every change in the intent.** The `intent` narration names every change a user or caller would notice, one sentence each, not only the main story. A branch that rate-limits orders and also starts pricing them from the catalogue names both.
- **Say totals from the screen.** A spoken total of a schedule or a count matches the numbers on screen: waits of 5 s doubling to 320 s add up to 635 s, "about ten and a half minutes", not "about nine". Add the numbers before you say the total.
- **`from` on each diagram.** Give each diagram scene that explains changed code `"from": ["h1", "h3"]`, the ids of at most 3 hunks it explains. The scene then shows a quiet "In the code: limiter.ts, server.ts" line, and the reading order says which chapter explains each hunk. Put a cited hunk's file name, or one of its identifiers as the code writes it (`checkLimit`, `MAX_REQUESTS`), in the scene's labels, since the viewer maps what they see onto the code. Give two scenes that cite hunks their own `chapter`, since each reading item names the chapter that explains it.
- **Explain what the reader needs to read the code.** The video does not have to cover every hunk. The reading order does.
- **The tests stay.** Keep the `tests` scene, with no test code.
- **End on a `reading` scene**, after the tests. For the branch it is required; for an explanation it is optional, and lists the snippets to read. Its `items` are the order to read the code in, main behaviour first, with related hunks together, as the code scenes of a reviewer's video would go. The order is grouped by the `topic` of the scene that explains each item, each topic once, and numbered in that order, so keep a topic's items together and the numbers you say will match. Each item is `{ "hunkId": "h1", "check": "the key resets on a new minute; check the off-by-one" }`: `check` says what to verify there, in under 80 characters, with the real values. Mark wiring, renames and config `"routine": true`, with no `check`; they go on one "skim" line. The file and lines come from `hunks.json`, so never type them. A new file's hunk is the whole file, so point at the lines that matter with `"lines": "40-58"`, inside the hunk's new lines. A `check` says what to verify and where, such as "the cursor's own row is returned again on the next page". Never write a list of nouns ("query bounds and ordering"), trivia, or "off by one" without saying where. Every substantial hunk must be an item or in `skipped`. The scene shows the first 6 items to read under "Read first" and counts the rest. Narrate only the first three and why they come first.
- **Point at the item.** For a claim the video cannot show, such as an off-by-one or a missing await, say "check this at item 2" in the narration, with the item's number in the reading order. Name only an item whose hunk the scene cites in `from`.
- **Review mode.** Flag each finding on the item of its hunk with `"flag": "<finding id>"`, never on a diagram step. The finding's line must be in that hunk's new lines. The item shows it in its severity's colour, such as "Claude: likely bug, the count is per server". A pre-read has no `review` scene: the reading scene is the one closing list, and `review.md` still lists the findings.

With `--audience preread`, `validate` writes `reading.md` in the run's directory, a checklist of the reading order with each topic once, and `outline` prints it as `1. src/limiter.ts:12-30  check` lines. A routine hunk of a file the order already lists goes on that file's item, as "also 1-6", never on a skim line. The player shows the same list in a Reading order panel beside the video, with "Copy as checklist" for the merge request.
