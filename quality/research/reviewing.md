# How expert developers review a merge request: evidence and storyboard rules

Method note. Many primary PDFs (ICSE/CSCW/ICSME) came back as unreadable binary through the fetch tool, and no PDF text extractor was installed. "Opened" below means I read the page text. "Snippet" means I only saw search-result abstracts or secondary summaries. I did not read any of the ordering theory's actual principles; that part is inference from abstracts. Nothing below is fabricated; gaps are marked.

## Source table

1. Bacchelli and Bird, ICSE 2013, "Expectations, outcomes, and challenges of modern code review". Finding: reviews are less about finding defects than people expect; knowledge sharing, awareness and alternative solutions matter, and understanding the code and the change is central, with weak tool support for it. Strength: strong (observation, interviews, survey, hundreds of classified comments at Microsoft). Access: abstract page only (Microsoft Research). The PDF was unreadable, so I have no numbers.
2. Sadowski et al., ICSE-SEIP 2018, "Modern code review: a case study at Google". Finding: Google's review is lightweight and tool-based, studied via 12 interviews, a 44-person survey and logs of 9 million reviewed changes. Strength: strong, large scale. Access: abstract page only; no results text. I do not report its specific findings (for example change size or speed) because I did not see them.
3. Baum, Schneider, Bacchelli, ICSME 2017, "On the optimal order of reading source code changes for review". Finding: an inductive theory, from interviews, a survey and related work, that an optimal order is mainly an optimal grouping of related change parts, formalized as a partial order. Strength: moderate (theory, not tested in this paper). Access: snippet (bibliographic abstract). I did not see the principles themselves, so "top-down vs bottom-up" is not verified from this source.
4. Baum, Schneider, Bacchelli, Empirical Software Engineering 2019, "Associating working memory capacity and code change ordering with code review performance". Finding: in a 50-participant experiment (mostly professionals, seeded defects), working memory capacity moderately associates with finding delocalized defects (defects whose cause spans several places) and hardly with other types; review effectiveness is significantly higher for small changes. Strength: moderate to strong (confirmatory experiment, small n). Access: snippet (search abstract). "The Choice of Code Review Process" could not be located; not covered.
5. Gonçalves et al., EMSE 2022, "Do explicit review strategies improve code review performance? Towards understanding the role of cognitive load". Finding: ad hoc vs checklist vs guided checklist; guided checklist helped more on a simple review, plain checklist helped efficiency and effectiveness on a complex one; no strong overall relationship between guidance and performance; participants were mostly novice reviewers. Strength: moderate (experiment, novice sample). Access: snippet.
6. Gonçalves, Calikli, Serebrenik, Bacchelli, CSCW 2023, "Competencies for code review". Finding: 27 competencies; technical ones rated essential and reviewers confident in them, but reviewers less confident in clear communication and constructive feedback. Strength: moderate (survey, n=105). Access: snippet. It says little about reading order.
7. Spadini et al., ICSE 2019, "Test-driven code review". Finding: in an experiment with 93 developers, reviewing tests first found the same share of production defects, more test-code defects, and fewer production maintainability issues; most developers still prefer production code first because they see it as more critical. Strength: moderate to strong. Access: snippet (several consistent search summaries).
8. Rigby and Bird, FSE 2013, "Convergent software peer review practices". Finding: review parameters converge across very different projects (Google, Microsoft, AMD, OSS); review raises the number of files a developer knows by 66 to 150 percent. Strength: strong (large data). Access: snippet. The five convergent practices were not confirmed from a primary source.
9. Tao et al., FSE 2012, "How do software engineers understand code changes?". Finding: understanding changes is indispensable; hardest information to get is a change's completeness, consistency and especially risk to other components; splitting composite changes into per-issue sub-changes would help but lacked tool support. Strength: moderate (industry exploratory). Access: snippet.
10. Kononenko, Baysal, Godfrey, ICSE 2016. Finding: in an 88-developer Mozilla survey, perceived review quality tied to thoroughness of feedback, reviewer familiarity with the code, and quality of the code itself. Strength: weak to moderate (self-report, one project). Access: snippet.
11. Ram et al., FSE 2018, "What makes a code change easier to review". Finding: reviewability depends on change description quality, change size and coherent commit history (literature survey, 10 interviews, tool rating 98 changes). Strength: moderate. Access: snippet. Author list not verified.
12. Google eng-practices, "Navigating a CL in review". Finding: (1) take a broad view: read the description, ask whether the change should exist at all; (2) examine the main parts first, the file(s) with the most logical change, looking for design problems before anything else; (3) review the rest in a logical sequence; reading tests first can help understand intent. Strength: expert practice, not empirical. Access: opened.
13. Google eng-practices, "What to look for in a code review". Finding: design, functionality, complexity, tests, naming, comments, style, consistency, documentation; read every line; consider context beyond the diff; praise good things. Does design first (do pieces interact sensibly, does it belong here, is now the right time). Strength: expert practice. Access: opened.
14. Pascarella et al., CSCW 2018, "Information needs in contemporary code review". Finding: card sort of 900 review comments from three open-source projects yields seven information needs. Strength: moderate (observational, OSS only). Access: abstract page opened; it does not list the seven. The list in the brief (alternative solution, correct understanding, rationale, code context, necessity, specialized expertise, splittable) is the requester's, which I could not verify; the one example I saw is knowing the uses of modified methods and variables (code context).
15. Greiler checklists. Finding: only secondary material found (a third-party 62-item checklist reportedly based on her work starts with change hygiene such as single concern and clear commit messages, then "does it do what it should" and simpler alternatives). Strength: practitioner. Access: snippet; not primary.
16. Newer file-order work (not requested, relevant). Fregnan et al. 2022 found files earlier in the list get more comments and bugs in lower files are noticed less (via a later paper's summary, ar5iv 2306.06956, opened). A 2025 mining study of 23,241 PRs (arXiv 2506.10654, abstract opened) found 44.6 percent were commented in non-alphabetical order; of those 20.6 percent largest-diff-first, 17.6 percent by title/description similarity, and 29 percent of PRs with tests and production code test-first. Authors conclude there is no single order reviewers use. Also a 2025 paper (Heander et al., arXiv 2507.09637) models review as decision making from reviewers' questions; PDF unreadable, content not seen.

## Synthesis

### 1. Reviewer questions, in the order experts ask them
Evidence is strongest for the first half (Google navigation, Bacchelli, Pascarella). The later order is practice-derived, not experimentally proven.
1. What is this and why? Read the description. Is the change necessary, and is now the right time? (Google step 1; Pascarella "necessity" and "rationale"; Ram on description quality.)
2. Is the approach right? Does it belong here, do the pieces fit, is there a simpler or alternative solution? (Google "design" and "main parts first"; Bacchelli alternative solutions; Pascarella alternative solution.)
3. Do I understand it? What is the context: who calls this, what else uses it? (Bacchelli, Pascarella correct understanding and code context; Tao.)
4. Is it correct, including edge cases and concurrency? Is it complete and consistent? (Google functionality; Tao completeness.)
5. What could break elsewhere? (Tao: risk to other components is the hardest information to obtain.)
6. Is it tested, and would the tests fail if the code broke? (Google tests; Spadini.)
7. Is it simple, well named and documented? Style last, as nits. (Google complexity, naming, comments, style.)
8. Should it be split? (Pascarella splittable; Ram on size.)

### 2. Best presentation order
- Open with purpose and risk: the problem, the user-visible or behavioral outcome, and the size and shape of the change. This answers question 1 and lets a viewer decide how closely to watch.
- Then design: the approach in two or three sentences, the main file(s), and one alternative considered if the diff shows one. Matches Google step 2.
- Then the core change, in logical order, grouping related parts across files (Baum's relatedness grouping) rather than alphabetical order. Within the group, show cause before effect: entry point or contract first, then implementation, then callers. I could not verify Baum's top-down vs bottom-up guidance; treat "contract first" as a defensible default, not a finding.
- Then the supporting changes (wiring, config, renames, generated files) briefly. Say what was skipped.
- Tests: show them after the behavior they check, as evidence ("this test proves X"), unless the change is a bug fix or the tests are the clearest spec, where showing the failing case first is better. Evidence: tests-first is neutral on production defects and better for test defects (Spadini), preferred by few developers; Google allows it as an aid to understanding; real reviewers do it in about 29 percent of mixed PRs.
- Close with risks and open questions: what could break, what was not verified, and anything that should be split.
- Keep the whole thing short: small changes review better (Baum 2019, Ram). Cap what a viewer must hold at once; delocalized defects are what working memory limits, so tell the viewer explicitly when a point depends on code seen earlier or elsewhere.

### 3. Audience differences
These are design inferences from the evidence, not tested findings. Kononenko supports that familiarity changes review quality; no source tested narrated walkthroughs.
- familiar (a reviewer of this change): skip background they know. Lead with what changed from their last view of the design, the decision points, and the risks. Spend time on design and risk, move fast through mechanical edits. Cover the "every line" duty by naming skipped parts rather than reading them.
- new (someone new to this code): add the context Pascarella lists (code context, rationale), define terms, and explain each hunk line by line in plain words, with what the surrounding code does shown first. Slower, and mostly follows file or logical order within groups. This is where Gonçalves' result that guidance helps simple reviews and novices argues for explicit structure. Still start with purpose and approach, then orient.
- overview (quick team overview): purpose, approach, impact, risk and test status only. Almost no code on screen; show one or two key hunks and the shape of the change (files, size). Name who should look closer and what to ask them.

### 4. Storyboard rules
1. Scene 1: title, problem and size of the change (files, lines, areas touched). Never open with the first file in the diff.
2. Scene 2: approach and why, one alternative if known, and the main file.
3. Order scenes by logical relatedness, not path. Each scene is one concern and may span files. Tell the viewer how this scene connects to the last.
4. Keep each scene to one idea; for a new audience name the surrounding code before the change.
5. Say what you skip and why (generated, rename, mechanical).
6. Put tests after the behavior they verify, with one line on what would fail if the code broke. For bug fixes, show the failing test or case first.
7. Flag risk spots explicitly: callers elsewhere, concurrency, migrations, config, public API. Tao says this is the information reviewers lack most.
8. End with verification status, open questions and a split suggestion if it mixes concerns.
9. Praise and nits: mention one good thing if real; keep style out unless it matters (Google).
10. Do not claim correctness. A narrated walkthrough should state what was and was not checked.

### Conflicts and tensions
- Tests first vs last. Google says the tool order is usual but tests-first can help understanding; Spadini finds it does not hurt production defects and helps test defects, but developers prefer production first; teaching guidance often says show the test as the spec. Resolution: default last as proof; first when the tests are the clearest statement of intent, or for bug fixes. Make this a per-change choice.
- Design first vs bottom-up teaching. Google reviews the main part first for design flaws. Teaching new people may need foundations (types, helpers) before the entry point. Resolution: state the approach in prose first for every audience, then for "new" go bottom-up or by dependency through the details.
- Importance order vs logical order. Largest-diff-first helps find the main part but a related Baum summary notes it can break the change's logical structure and confuse. Resolution: pick the main concern first, then follow logical grouping.
- Exhaustiveness vs brevity. Google says read every line; viewers will not sit through all of it. Resolution: name skipped parts; give the full line walk only for "new".
- Checklists. Gonçalves found no strong overall benefit, with mixed effects by task difficulty and mostly novice participants. Do not read out a checklist; use the question order above as scene structure, not a spoken list.
- Weak evidence overall: most findings are observational or from small experiments; no study tested video walkthroughs.
